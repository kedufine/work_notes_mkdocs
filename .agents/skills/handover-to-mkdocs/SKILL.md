# 인수인계 자료 변환·등록

인수인계 자료 원본을 빠짐없이 읽어, 인수자가 읽고 바로 이해할 수 있는 MkDocs 문서로 다시 쓰는 절차입니다. `AGENTS.md`의 처리 과정 가운데 **1단계(기계적 변환)와 2단계(통합 문서 작성·등록)**를 정하며, 진행 상태를 `manifest.json`에 기록합니다. 3단계(질문지 작성)와 4단계(답변 반영)는 `.agents/skills/handover-questionnaire/SKILL.md`에 있습니다.

이 스킬은 **무엇을 어떻게 재구성하고 무엇을 보존하는지**를 정합니다. 결과 문서의 골격과 문법(제목 구조, 표, 다이어그램, 알림 상자, `nav`, 홈 갱신, 빌드 검증)은 `.agents/skills/mkdocs-writing-guide/SKILL.md`를 따릅니다.

## 1. 폴더와 산출물

| 경로 | 역할 | Git |
| :--- | :--- | :--- |
| `1. RAW/` | 사용자가 받은 인수인계 자료가 건별 폴더(예: `업무인수인계_조호재/`)로 들어오는 곳입니다. **에이전트는 이 폴더의 파일을 수정·이동·삭제하지 않습니다.** | 제외 |
| `2. 변환 중간본/` | 1단계 스크립트가 만드는 파일별 마크다운, `manifest.json`, `변환 보고서.md`입니다. 스크립트가 다시 만들 때 덮어쓰므로 직접 고치지 않습니다. | 제외 |
| `mkdocs/docs/handover/` | 2단계에서 작성하는 인수인계 문서입니다. **마스터 허브(`index.md`)와 건별 통합 문서(`<건별-슬러그>/index.md`)**로 구성됩니다. | 포함 |

## 2. 사전 점검

작업을 시작할 때마다 먼저 도구를 확인합니다.

```bash
.venv/bin/python .agents/skills/handover-to-mkdocs/scripts/convert.py --check       # macOS
.venv/Scripts/python .agents/skills/handover-to-mkdocs/scripts/convert.py --check   # Windows
```

이 문서의 이후 명령은 macOS 경로로 적습니다. Windows에서는 `.venv/bin/python`을 `.venv/Scripts/python`으로 바꾸고, 경로 구분자는 `/`를 그대로 사용합니다(`AGENTS.md`의 필수 규칙). 변환 스크립트는 표준 라이브러리만 쓰므로, `.venv`가 아직 없으면 `--check`는 시스템 파이썬(`python3`, Windows는 `py`)으로 실행합니다.

사용자 PC에는 **아무 프로그램도 설치되어 있지 않을 수 있다**고 가정합니다. 문서 사이트는 `.venv`에 설치된 Python, MkDocs, Material for MkDocs(`mkdocs-material`)가 있어야 빌드·실행되고, 변환은 Node.js, kordoc, OfficeCLI가 있어야 합니다. `--check`는 이 여섯 항목(`python`, `mkdocs`, `mkdocs-material`, `node`, `kordoc`, `officecli`)을 모두 확인합니다.

- 여섯 항목 가운데 `없음`이 하나라도 있으면, 사용자에게 알린 뒤 설치 스크립트를 실행합니다. 설치 스크립트는 없는 프로그램만 설치합니다.
- 시스템 파이썬도 없어서 `--check`를 실행할 수 없으면(`python3`·`py`를 찾을 수 없음, 또는 Windows에서 `python`을 입력하면 Microsoft Store가 열림), 확인을 건너뛰고 바로 설치 스크립트를 실행합니다. 설치 스크립트가 파이썬부터 설치합니다.

- macOS: `bash setup/setup-mac.sh`
- Windows: `powershell -NoProfile -ExecutionPolicy Bypass -File setup/setup-windows.ps1` (`-Pause`는 넘기지 않습니다. 넘기면 끝에서 Enter 입력을 기다리며 멈춥니다.)

에이전트가 대신할 수 없는 일(macOS에서 Homebrew 설치에 필요한 암호 입력, Windows의 사용자 계정 컨트롤 승인·Microsoft Store 설치, 인터넷 연결 문제)을 만나면, 설치 스크립트가 `[사용자 조치 필요]` 안내를 출력하고 종료 코드 3으로 끝납니다. 이때는 `AGENTS.md`의 "사용자 조치 절차"대로 안내를 그대로 전달하고 멈춘 뒤, 사용자가 "했어"라고 하면 같은 명령을 다시 실행해 이어서 진행합니다. Windows 설치 스크립트를 실행하기 전에는 UAC 창이 뜰 수 있다고 먼저 알립니다.

설치 스크립트가 실패하면 `README.md` 2절(수동 설치)의 해당 단계를 따릅니다. kordoc을 직접 설치할 때는 OCR 엔진이 빠지지 않도록 `npm install -g kordoc --allow-scripts=onnxruntime-node,protobufjs`를 사용합니다. 원문 안내는 <https://github.com/chrisryugj/kordoc>, <https://github.com/iOfficeAI/OfficeCLI>에 있습니다. 설치 뒤에도 `없음`이 나오면 새 터미널에서 다시 확인합니다.

## 3. 1단계: 원본 전체를 중간본으로 변환

```bash
.venv/bin/python .agents/skills/handover-to-mkdocs/scripts/convert.py --dry-run   # 대상 목록과 처리 경로만 확인
.venv/bin/python .agents/skills/handover-to-mkdocs/scripts/convert.py             # 변환 실행
```

스크립트는 원본 폴더를 하위 폴더까지 모두 훑고, 형식에 따라 다음 도구로 변환합니다.

| 형식 | 도구 | 비고 |
| :--- | :--- | :--- |
| `.hwp` `.hwpx` `.hwpml` `.hml` | kordoc | 표·병합 셀 보존 |
| `.pdf` | kordoc | 스캔 PDF(`IMAGE_BASED_PDF`)는 OCR을 켜고 자동 재시도 |
| `.docx` `.xlsx` | kordoc → 실패 시 OfficeCLI | |
| `.xls` `.docm` `.xlsm` | kordoc | |
| `.pptx` | OfficeCLI | kordoc은 PPTX를 지원하지 않음. 슬라이드별 `## 슬라이드 N` 제목으로 변환 |
| `.png` `.jpg` `.jpeg` `.webp` | kordoc | 내장 OCR |
| `.txt` `.md` `.csv` `.tsv` | 스크립트 | UTF-8·CP949 자동 판별, CSV는 표로 변환(최대 500행) |
| `.doc` `.ppt` `.rtf`, 압축 파일 등 | 변환 안 함 | 보고서에 조치 방법(다시 저장, 압축 해제)을 기록 |

- `~$`로 시작하는 Office 잠금 파일, 숨김 파일, `Thumbs.db`, `desktop.ini`는 제외합니다.
- 중간본은 `2. 변환 중간본/<8자리 ID>_<원본 파일명>.md`로 평탄하게 저장합니다. ID는 원본 상대 경로의 해시이므로 같은 파일은 항상 같은 ID를 받습니다. kordoc이 추출한 그림은 `2. 변환 중간본/images/<중간본 이름>/`에 저장됩니다.
- 원본 해시가 바뀌지 않은 파일은 다시 변환하지 않습니다. 중간에 끊겨도 같은 명령을 다시 실행하면 이어서 진행됩니다. 실패한 파일은 매번 다시 시도합니다.
- 파일이 많으면 명령을 백그라운드로 실행하고 끝날 때까지 기다립니다. 진행 중에 파일을 하나씩 따로 변환하지 않습니다.

### 3.1 manifest.json 필드

최상위에는 `version`, `updated_at`(마지막 실행 시각), `tools`(도구 버전), `files`(원본 ID → 항목)가 있습니다. 각 항목의 필드는 다음과 같습니다.

| 필드 | 뜻 |
| :--- | :--- |
| `id` | 원본 상대 경로의 해시 8자리. `files`의 키와 같습니다. |
| `source`, `ext`, `size`, `sha256` | 원본 폴더 기준 상대 경로(NFC), 확장자, 크기, 내용 해시 |
| `status` | `converted`, `empty`, `failed`, `unsupported`, `removed` |
| `tool`, `error_code`, `error`, `hint` | 사용한 도구, 실패 코드, 오류 원문, 조치 방법 |
| `output`, `images`, `chars` | 중간본 파일명, 그림 폴더(`2. 변환 중간본/` 기준), 중간본 글자 수 |
| `ocr` | 스캔 PDF라서 OCR로 다시 변환했으면 `true` |
| `modified` | 원본 파일의 수정일 |
| `published` | 이 원본을 반영한 MkDocs 문서 경로 목록(**2단계에서 에이전트가 기록**, `handover/<건별-슬러그>/index.md`) |
| `needs_republish` | 원본이 바뀌거나 삭제되어 문서를 고쳐야 하면 `true`(**반영 후 에이전트가 `false`로 변경**) |

스크립트는 재실행해도 `published`와 `needs_republish`를 보존합니다. 에이전트가 고치는 필드는 이 두 개뿐입니다.

### 3.2 변환 결과 점검

`2. 변환 중간본/변환 보고서.md`를 읽고 다음을 사용자에게 보고합니다.

- 상태별 개수와 **조치가 필요한 파일**(실패, 미지원, 빈 결과) 목록과 조치 방법
- 사용자가 조치할 수 있는 항목(암호 해제, `.doc`→`.docx` 다시 저장, 압축 해제)이 있으면 조치 후 1단계를 다시 실행하도록 안내합니다. 이 항목 때문에 2단계를 멈추지는 않습니다.

## 4. 2단계: 인수자를 위한 통합 문서 작성과 MkDocs 등록

2단계의 목표는 **인수자가 이 문서 하나만 읽고 업무를 파악해 바로 수행할 수 있게 하는 것**입니다. 인수인계 건마다 하나의 마크다운 문서를 작성합니다.

> **요약 문서가 아닙니다.** 이 작업은 원본의 내용을 줄이는 요약이 아니고 원본을 그대로 옮기는 전사도 아닙니다. **원본의 내용을 하나도 생략하지 않고 새로운 골격에 가독성 높게 다시 배치하는 재구성**입니다. 바꾸는 것은 구성과 표현(순서, 묶음, 표·다이어그램·차트, 문장)이고, 줄어드는 것은 여러 파일에 똑같이 반복된 내용뿐입니다. 문서가 길어지는 것은 문제가 아니며, 분량을 줄이려고 내용을 덜어 내지 않습니다.

### 4.0 인수인계 건(Package) 식별 및 영문 슬러그 규칙

1. `1. RAW/` 바로 아래의 최상위 폴더가 개별 인수인계 건(패키지)의 단위입니다 (예: `1. RAW/업무인수인계_조호재/`).
2. 폴더명과 자료의 내용에서 **기준 연도, 담당자명(인계자)**을 파악하여 영문 소문자·숫자·하이픈 조합의 고유 슬러그를 만듭니다.
    - 규칙: `YYYY-<person-name>` (예: `2024-cho-hojae`). 같은 해에 같은 인계자의 건이 둘 이상이면 `-<topic>`을 덧붙여 구별합니다.
3. **기준 연도 판별**:
    - 폴더명에 연도가 없거나 오타(예: `2004년 조호재 인수인계 자료`와 같이 2024년이 잘못 적힌 경우)가 있을 때는, 원본 파일들의 작성일·수정일 및 문서 본문(예: 2023년 말 협의 결과, 2024년 사업 계획 등)을 대조하여 실제 기준 연도를 판별합니다.
    - 오타가 포함된 슬러그나 메뉴명을 쓰지 않고 올바른 실제 연도 슬러그(예: `2024-cho-hojae`)와 nav 한글 명칭(`2024년 조호재`)을 부여합니다.
4. 한 건의 문서는 `mkdocs/docs/handover/<건별-슬러그>/index.md` **하나**입니다. 원본 파일별·주제별로 문서를 나누지 않습니다.

### 4.1 내용 파악과 장 구성 설계

1. 해당 건의 중간본을 **모두 읽습니다**(`converted`, `empty`, 텍스트를 확인할 수 있는 `unsupported`). 일부만 읽고 문서를 쓰기 시작하지 않습니다.
2. 내용을 원본 파일 단위가 아니라 **업무 단위**로 다시 묶습니다. 한 업무에 관한 설명이 인수인계서, 매뉴얼, 공문, 메신저 캡처에 흩어져 있으면 한 절로 모읍니다.
3. `mkdocs-writing-guide` 4.2절의 골격을 기준으로 장 구성을 정합니다. 자료에 해당 내용이 없는 장은 만들지 않고, 자료의 성격에 맞는 장이 더 필요하면 추가합니다.
4. 장 구성안(장 제목, 장마다 반영할 원본)을 사용자에게 제시하고, 답을 기다리지 않고 작성을 이어갑니다.

### 4.2 재구성 원칙 (가독성)

- **읽는 순서를 인수자의 관점으로 정합니다.** 전체 업무의 윤곽(무엇을, 언제, 누구와)을 먼저 보여 주고, 그다음에 업무별 상세 절차, 참고 원문의 순서로 배치합니다. 원본 폴더의 순서나 파일명 순서를 따르지 않습니다.
- **줄글을 구조화합니다.** 긴 문단은 표, 번호 절차, 다이어그램으로 바꾸고, 내용의 성격에 따라 아래 표현을 선택합니다.

| 내용의 성격 | 표현 |
| :--- | :--- |
| 업무 목록, 담당·연락처, 계정·권한, 판본 비교, 주기별 일정 | 마크다운 표 |
| 업무 처리 순서, 결재·협의 흐름, 분기가 있는 절차 | Mermaid `flowchart` |
| 부서·시스템 사이에 주고받는 요청과 회신 | Mermaid `sequenceDiagram` |
| 문서나 건의 상태 변화(접수 → 검토 → 완료) | Mermaid `stateDiagram-v2` |
| 건수·예산·실적처럼 수치가 여러 개인 자료의 추이와 비교 | Vega-Lite 차트 (수치는 표로도 함께 제시) |
| 분기 없이 순서대로 실행하는 단계 | 번호 목록 |
| 놓치면 문제가 되는 기한, 주의 사항 | 알림 상자(`!!! warning`) |
| 공문 전문, SQL·스크립트, 수십 행이 넘는 표 | 접이식 블록(`??? note "원문: 파일명"`) |

- **다이어그램과 차트는 이해를 돕는 곳에 적극적으로 넣습니다.** 단계가 3개 이상이거나 분기·담당 전환이 있는 절차는 다이어그램으로 그리고, 수치 자료가 있으면 차트를 검토합니다. 다만 표 한 개로 충분한 내용을 꾸미기 위해 넣지 않습니다. 작성 규칙과 미리 보기는 `mkdocs-writing-guide` 5.3·5.4절을 따릅니다.
- **똑같이 반복된 내용만 합칩니다.** 같은 내용이 여러 판본(초안, 구버전, 최종안)이나 여러 파일에 있으면 최신 판본을 기준으로 한 번만 쓰고, 판본 사이에 달라진 점은 표로 정리합니다. 한쪽 파일에만 있는 내용은 중복이 아니므로 반드시 반영합니다.
- **질의와 회신, 협의 경위는 결론부터 씁니다.** "무엇이 문제였고, 어떻게 결론이 났으며, 인수자가 할 일은 무엇인가"를 먼저 적고, 경위는 시간순 표로 정리합니다.
- **용어를 풀어 씁니다.** 원문에 설명 없이 쓰인 내부 용어와 약어는, 자료의 다른 부분에서 뜻을 확인할 수 있으면 처음 나오는 곳에 풀이를 덧붙입니다. 확인할 수 없으면 `확인 필요`로 표시하고 질문지에 넣습니다.

### 4.3 내용 보존 원칙 (바꾸면 안 되는 것)

표현은 바꾸지만 **내용은 줄이지 않고, 사실은 바꾸지 않습니다.**

- **본문의 내용을 생략하지 않습니다.** 원본에 적힌 설명, 배경, 경위, 단서 조항, 예외, 비고는 사소해 보이더라도 모두 문서의 알맞은 절에 들어가야 합니다. "주요 내용만", "핵심만" 골라 싣지 않으며, "등", "기타", "이하 생략"으로 줄이지 않습니다. 표의 행과 목록의 항목도 일부만 고르지 않고 전부 옮깁니다.
- **표현 방식을 바꾸는 것은 생략이 아닙니다.** 문단을 표나 다이어그램으로 바꿀 때는 그 문단의 정보가 표의 칸, 노드와 연결선, 도표 아래의 설명 가운데 어딘가에 모두 남아 있어야 합니다. 다이어그램에 담지 못한 조건이나 단서는 도표 바로 아래에 불릿으로 적습니다.
- **사실을 빠뜨리지 않습니다.** 수치, 날짜, 금액, 기관·부서·사람 이름, 연락처, 계정, 접속 주소, 메뉴 경로, 문서 번호는 원문의 값 그대로 옮깁니다. 사이트는 사용자 본인만 보므로 개인정보를 가리지 않습니다.
- **추측으로 채우지 않습니다.** 자료에 없는 단계, 담당, 일정을 그럴듯하게 만들어 넣지 않습니다. 비어 있는 부분은 `확인 필요`라고 적고 `## 인수인계 확인 사항`의 `**미결 사항**`에 모읍니다.
- **다이어그램과 차트에는 원문에 근거가 있는 단계와 수치만 넣습니다.** 흐름을 매끄럽게 보이게 하려고 원문에 없는 노드나 값을 추가하지 않습니다.
- **출처를 적습니다.** `###` 단위의 절 끝에 `출처: \`별첨자료/파일명.hwp\``와 같이 근거가 된 원본의 경로를 적어서, 인수자가 원본을 찾아볼 수 있게 합니다. 문서와 질문지에 적는 원본 경로는 모두 **건 폴더 기준 상대 경로**이며, 건 폴더의 이름은 `## 요약` 표의 `**원본 자료**` 행에 적습니다.
- **전문이 필요한 자료는 접이식 블록에 그대로 둡니다.** 실행해야 하는 SQL·스크립트, 문구가 중요한 공문·지침, 값을 그대로 써야 하는 큰 표는 `??? note` 블록에 전문을 넣습니다. 블록 위에는 그 자료의 내용을 재구성한 설명(무엇을 하는 쿼리인지, 공문이 무엇을 정하는지)을 두며, 전문을 넣었다는 이유로 설명을 생략하지 않습니다.
    - 공공기관 및 Windows 환경에서 작성된 스크립트·SQL 파일은 종종 **`UTF-16LE`(BOM 포함) 또는 `CP949`**로 인코딩되어 일반 텍스트 읽기에서 실패하거나 바이너리로 취급될 수 있습니다. Python(`open(..., encoding='utf-16le', errors='replace')`) 등으로 내용을 정확히 확인한 뒤 코드 블록(` ```sql `, ` ```bash `)으로 전문을 수록합니다.
- **모든 원본을 추적합니다.** 내용이 거의 없는 파일(빈 양식, 메모)을 포함하여 해당 건의 모든 원본이 문서의 `원본 파일 대응표`에 들어 있어야 합니다. 반영한 원본(`converted`·`empty`, 그리고 `.sql`처럼 에이전트가 텍스트로 직접 읽어 반영한 `unsupported`)에는 반영한 절을, 반영하지 못한 원본(`failed`와 나머지 `unsupported`)에는 상태와 조치 방법을 적습니다.
- **작성을 마친 뒤 대조합니다.** 중간본을 파일별로 처음부터 끝까지 다시 훑으면서, 문단·표·목록 하나하나가 문서의 어느 절에 반영되었는지 확인합니다. 반영되지 않은 내용이 있으면 보충하고, 문서의 분량이 중간본에 비해 눈에 띄게 적다면 요약된 부분이 없는지 다시 확인합니다.

### 4.4 문서 골격

`mkdocs-writing-guide` 4.2절의 **인수인계 통합 문서 골격**을 따릅니다.

### 4.5 경로, 이미지, 네비게이션

- **문서 파일 경로**: `mkdocs/docs/handover/<건별-슬러그>/index.md`
- **이미지 경로 및 포맷 변환 (필수)**:
    - 경로: `mkdocs/docs/handover/<건별-슬러그>/images/` (파일명은 영문 소문자·숫자·하이픈)
    - **BMP 포맷의 PNG 변환**: HWP/HWPX 문서에서 추출된 이미지가 `.bmp` 포맷인 경우, 웹 브라우저(Chrome, Safari 등)에서 정상 렌더링되지 않거나 용량(장당 수 MB)으로 인해 로딩이 지연됩니다. 전용 폴더로 이전할 때 반드시 **Pillow(PIL) 라이브러리를 사용하여 `.png`로 변환**하여 저장하고 마크다운 본문에도 `.png` 확장자로 링크합니다.
    - **불필요한 공문 직인/로고 제외**: 공문서 하단에 관행적으로 반복 첨부되는 기관 직인/도장/로고(예: KERIS 직인 `image_001.png` 등 22KB 내외 동일 이미지)는 이전 대상에서 제외하고, 본문 이해에 필수적인 **시스템 UI 캡처 화면만 선별 이전**합니다. 이미지에는 무엇을 보여 주는 화면인지 설명을 함께 적습니다.
- **네비게이션(`nav`) 등록**:
    - `인수인계` 탭의 첫 항목은 항상 마스터 허브인 `handover/index.md`입니다.
    - 그 아래에 인수인계 건마다 통합 문서를 한 항목으로 등록합니다.
    - **좌측 메뉴 폭 제한 및 한 줄 표시 규칙 (필수)**: 좌측 사이드바 메뉴는 폭이 제한되어 있어 글자 수가 길어지면 두 줄로 줄바꿈됩니다. 따라서 메뉴명에 부서나 업무명(예: `(K-에듀파인 업무관리)`)을 덧붙이지 않고, 반드시 **`YYYY년 <담당자명>`** (예: `2024년 조호재`) 형태로 지정합니다. 소관 업무 및 부서 등의 상세 정보는 통합 문서의 `## 요약`과 마스터 허브 표에 적습니다.

```yaml
nav:
  - 홈: index.md
  - 인수인계:
      - handover/index.md # 마스터 허브 (전체 인수인계 목록)
      - 2024년 조호재: handover/2024-cho-hojae/index.md # 건별 통합 문서
      - 2025년 홍길동: handover/2025-hong-gildong/index.md # 향후 추가 건 예시
```

### 4.6 마스터 허브와 홈

1. **마스터 허브 페이지 (`mkdocs/docs/handover/index.md`)**:
    - 사이트의 모든 인수인계 건을 총괄 안내하는 포털 페이지입니다.
    - `## 요약`: 전체 인수인계 건 목록 표 (인수인계 건명, 담당자/부서, 소관 업무/시스템, 기준 연월, 원본 수, 상태, 통합 문서 바로가기 링크).
    - `상태`에는 진행 단계를 적습니다: `1차 등록`(2단계 완료) → `질문지 회신 대기`(3단계 완료) → `일부 미회신` 또는 `보강 완료`(4단계 완료).
    - `## 1. 등록된 인수인계 건별 안내`: 각 건의 소관 업무, 주요 내용, 바로가기 링크.
    - `## 2. 인수인계 자료 탐색 및 신규 등록 가이드`: 사이드바 탐색 및 추가 절차 안내.
2. **홈(`mkdocs/docs/index.md`)**: 요약 표의 `인수인계 자료` 행과 최근 업데이트 표의 건별 행을 `mkdocs-writing-guide` 3.4절에 따라 갱신합니다.

### 4.7 manifest 일괄 갱신 가이드

- 통합 문서에 반영한 원본 항목의 `published`에 통합 문서의 경로(`handover/<건별-슬러그>/index.md`)를 배열로 기록하고, `needs_republish`를 `false`로 설정합니다.
- 반영하지 못한 원본(`failed`, 내용을 확인하지 못한 `unsupported`)은 `published`에 넣지 않습니다.
- 원본이 많으면 누락이 생기기 쉬우므로 Python 스크립트로 일괄 갱신합니다:
    ```python
    import json
    with open('2. 변환 중간본/manifest.json', 'r', encoding='utf-8') as f:
        data = json.load(f)
    prefix, doc = '업무인수인계_조호재/', 'handover/2024-cho-hojae/index.md'
    read_directly = {'<file-id>'}  # 텍스트로 직접 읽어 반영한 unsupported 원본의 ID
    for fid, entry in data['files'].items():
        if not entry['source'].startswith(prefix):
            continue
        if entry['status'] in ('converted', 'empty') or fid in read_directly:
            entry['published'] = [doc]
            entry['needs_republish'] = False
    with open('2. 변환 중간본/manifest.json', 'w', encoding='utf-8') as f:
        json.dump(data, f, ensure_ascii=False, indent=2)
    ```

### 4.8 등록 후 이어지는 단계 (질문지 작성)

2단계가 끝나면 사용자에게 묻지 않고 `.agents/skills/handover-questionnaire/SKILL.md`를 읽어 3단계(질문지 작성)를 이어서 수행합니다.

- 문서를 쓰는 동안 `확인 필요`로 표시한 부분과 `## 인수인계 확인 사항`의 `**미결 사항**`(절차·담당·일정이 빠진 부분, 본문에서 언급되지만 받지 못한 파일, 자료 간 불일치)이 3단계에서 질문을 뽑는 출발점이 됩니다.
- 변환하지 못한 원본(`failed`, `unsupported`) 가운데 사용자가 조치할 수 없는 것(인계자만 가진 암호, 인계자 PC에만 있는 파일)은 질문지에 `자료 누락` 유형으로 넣습니다.

## 5. 원본이 바뀌었을 때 (증분 갱신)

1. `convert.py`를 다시 실행합니다. 새 파일만 변환되고, 바뀐 파일은 재변환되며, 삭제된 파일은 `removed`로 표시됩니다.
2. 기존 인수인계 건에 파일이 추가·변경된 경우에는 그 건의 통합 문서(`handover/<건별-슬러그>/index.md`)에서 해당 업무의 절을 고쳐 씁니다. 문서를 새로 나누어 만들지 않으며, 원본 파일 대응표와 최종 수정일을 갱신합니다.
3. 완전히 새로운 인수인계 건(새 상위 폴더)이 들어온 경우:
    - 새 건별 슬러그 디렉터리와 통합 문서(`index.md`) 작성
    - `mkdocs.yml`의 `nav`에 새 인수인계 건 항목 추가
    - 마스터 허브(`handover/index.md`) 표에 새 건 행 추가
    - 홈(`index.md`) 최근 업데이트 표 갱신
4. `manifest.json`을 갱신하고 빌드 검증을 수행합니다.
5. 완전히 새로운 인수인계 건이면 4.8절에 따라 3단계(질문지 작성)까지 수행합니다. 기존 건에 자료가 추가된 경우에는 새 자료에서 생긴 의문점을 사용자에게 보고하고, 사용자가 요청하면 새 작성일로 질문지를 하나 더 만듭니다.
6. 통합 문서가 4단계에서 이미 보강되어 있다면, 원본 변경을 반영할 때 질문지 답변으로 채운 내용(`질문지 YYMMDD · Q-NNN` 표기가 붙은 부분)과 `## 인계자 보충 답변` 섹션을 지우지 않고 보존합니다.
