# 인수인계 자료 변환·등록

인수인계 자료 원본을 빠짐없이 읽어, 인수자가 읽고 바로 이해할 수 있는 MkDocs 문서로 다시 쓰는 절차입니다. `AGENTS.md`의 처리 과정 가운데 **1단계(기계적 변환)와 2단계(건별 문서 작성·등록)**를 정하며, 진행 상태를 `manifest.json`에 기록합니다. 등록한 뒤 문서에 없는 내용을 질문받았을 때 원본을 찾아 답하는 방법(6절)도 이 스킬에서 정합니다. 3단계(질문지 작성)와 4단계(답변 반영)는 `.agents/skills/handover-questionnaire/SKILL.md`에 있습니다.

이 스킬은 **무엇을 어떻게 재구성하고 무엇을 보존하는지**를 정합니다. 결과 문서의 골격과 문법(제목 구조, 표, 다이어그램, 알림 상자, `nav`, 홈 갱신, 빌드 검증)은 `.agents/skills/mkdocs-writing-guide/SKILL.md`를 따릅니다.

## 1. 폴더와 산출물

| 경로 | 역할 | Git |
| :--- | :--- | :--- |
| `1. RAW/` | 사용자가 받은 인수인계 자료가 건별 폴더(예: `업무인수인계_홍길동/`)로 들어오는 곳입니다. **에이전트는 이 폴더의 파일을 수정·이동·삭제하지 않습니다.** | 제외 |
| `2. 변환 중간본/` | 1단계 스크립트가 만드는 파일별 마크다운, `manifest.json`, `변환 보고서.md`입니다. 스크립트가 다시 만들 때 덮어쓰므로 직접 고치지 않습니다. | 제외 |
| `mkdocs/docs/handover/` | 2단계에서 작성하는 인수인계 문서입니다. **마스터 허브(`index.md`)와 건별 폴더(`<건별-슬러그>/`)**로 구성되며, 건별 폴더에는 개요 문서(`index.md`)와 필요한 만큼의 하위 문서(`<주제>.md`)가 들어갑니다. | 포함 |

## 2. 사전 점검

작업을 시작할 때마다 먼저 도구를 확인합니다.

```bash
.venv/bin/python .agents/skills/handover-to-mkdocs/scripts/convert.py --check       # macOS
.venv/Scripts/python .agents/skills/handover-to-mkdocs/scripts/convert.py --check   # Windows
```

이 문서의 이후 명령은 macOS 경로로 적습니다. Windows에서는 `.venv/bin/python`을 `.venv/Scripts/python`으로 바꾸고, 경로 구분자는 `/`를 그대로 사용합니다(`AGENTS.md`의 필수 규칙). 변환 스크립트는 표준 라이브러리만 쓰므로, `.venv`가 아직 없으면 `--check`는 시스템 파이썬(`python3`, Windows는 `py`)으로 실행합니다.

사용자 PC에는 **아무 프로그램도 설치되어 있지 않을 수 있다**고 가정합니다. 문서 사이트는 `.venv`에 설치된 Python, MkDocs, Material for MkDocs(`mkdocs-material`)가 있어야 빌드·실행되고, 변환은 Node.js, kordoc, OfficeCLI가 있어야 합니다. `--check`는 이 여섯 항목(`python`, `mkdocs`, `mkdocs-material`, `node`, `kordoc`, `officecli`)을 모두 확인합니다.

- 여섯 항목 가운데 `없음`이 하나라도 있으면, 사용자에게 알린 뒤 설치 스크립트를 실행합니다. 설치 스크립트는 없는 프로그램만 설치합니다.
- 시스템 파이썬도 없어서 `--check`를 실행할 수 없으면(`python3`·`py`를 찾을 수 없음, 또는 Windows에서 `python`을 입력하면 Microsoft Store가 열림), 확인을 건너뛰고 바로 설치 스크립트를 실행합니다. 설치 스크립트가 파이썬부터 설치합니다.

- macOS: `bash setup/setup-mac.sh`
- Windows: `powershell -NoProfile -ExecutionPolicy Bypass -File setup/setup-windows.ps1` (`-Pause`는 넘기지 않습니다. 넘기면 끝에서 Enter 입력을 기다리며 멈춥니다.)

에이전트가 대신할 수 없는 일(macOS에서 Homebrew 설치에 필요한 암호 입력, Windows의 사용자 계정 컨트롤 승인·Microsoft Store 설치, 인터넷 연결 문제)을 만나면, 설치 스크립트가 `[사용자 조치 필요]` 안내를 출력하고 종료 코드 3으로 끝납니다. 이때는 `AGENTS.md`의 "사용자 조치 절차"대로 안내를 그대로 전달하고 멈춘 뒤, 사용자가 "했어"라고 하면 같은 명령을 다시 실행해 이어서 진행합니다. Windows 설치 스크립트를 실행하기 전에는 UAC 창이 뜰 수 있다고 먼저 알립니다.

설치 스크립트가 실패하면 `README.md` 2절(수동 설치)의 해당 단계를 따릅니다. kordoc을 직접 설치할 때는 OCR 엔진이 빠지지 않도록 `npm install -g kordoc --allow-scripts=onnxruntime-node,protobufjs`를 사용합니다. 원문 안내는 <https://github.com/chrisryugj/kordoc>, <https://github.com/iOfficeAI/OfficeCLI>에 있습니다. 설치 뒤에도 `없음`이 나오면 새 터미널에서 다시 확인합니다.

## 3. 1단계: 원본 전체를 중간본으로 변환

```bash
.venv/bin/python .agents/skills/handover-to-mkdocs/scripts/convert.py --dry-run   # 대상 목록과 처리 경로만 확인
.venv/bin/python .agents/skills/handover-to-mkdocs/scripts/convert.py             # 변환 실행
```

스크립트는 원본 폴더를 하위 폴더까지 모두 훑고, 형식에 따라 다음 도구로 변환합니다.

| 형식 | 도구 | 비고 |
| :--- | :--- | :--- |
| `.hwp` `.hwpx` `.hwpml` `.hml` | kordoc | 표·병합 셀 보존 |
| `.pdf` | kordoc | 스캔 PDF(`IMAGE_BASED_PDF`)는 OCR을 켜고 자동 재시도 |
| `.docx` `.xlsx` | kordoc → 실패 시 OfficeCLI | |
| `.xls` `.docm` `.xlsm` | kordoc | |
| `.pptx` | OfficeCLI | kordoc은 PPTX를 지원하지 않음. 슬라이드별 `## 슬라이드 N` 제목으로 변환 |
| `.png` `.jpg` `.jpeg` `.webp` | kordoc | 내장 OCR |
| `.txt` `.md` `.csv` `.tsv` | 스크립트 | UTF-8·CP949 자동 판별, CSV는 표로 변환(최대 500행) |
| `.doc` `.ppt` `.rtf`, 압축 파일 등 | 변환 안 함 | 보고서에 조치 방법(다시 저장, 압축 해제)을 기록 |

- `~$`로 시작하는 Office 잠금 파일, 숨김 파일, `Thumbs.db`, `desktop.ini`는 제외합니다.
- 중간본은 `2. 변환 중간본/<8자리 ID>_<원본 파일명>.md`로 평탄하게 저장합니다. ID는 원본 상대 경로의 해시이므로 같은 파일은 항상 같은 ID를 받습니다. kordoc이 추출한 그림은 `2. 변환 중간본/images/<중간본 이름>/`에 저장됩니다.
- 원본 해시가 바뀌지 않은 파일은 다시 변환하지 않습니다. 중간에 끊겨도 같은 명령을 다시 실행하면 이어서 진행됩니다. 실패한 파일은 매번 다시 시도합니다.
- 파일이 많으면 명령을 백그라운드로 실행하고 끝날 때까지 기다립니다. 진행 중에 파일을 하나씩 따로 변환하지 않습니다.

### 3.1 manifest.json 필드

최상위에는 `version`, `updated_at`(마지막 실행 시각), `tools`(도구 버전), `files`(원본 ID → 항목)가 있습니다. 각 항목의 필드는 다음과 같습니다.

| 필드 | 뜻 |
| :--- | :--- |
| `id` | 원본 상대 경로의 해시 8자리. `files`의 키와 같습니다. |
| `source`, `ext`, `size`, `sha256` | 원본 폴더 기준 상대 경로(NFC), 확장자, 크기, 내용 해시 |
| `status` | `converted`, `empty`, `failed`, `unsupported`, `removed` |
| `tool`, `error_code`, `error`, `hint` | 사용한 도구, 실패 코드, 오류 원문, 조치 방법 |
| `output`, `images`, `chars` | 중간본 파일명, 그림 폴더(`2. 변환 중간본/` 기준), 중간본 글자 수 |
| `ocr` | 스캔 PDF라서 OCR로 다시 변환했으면 `true` |
| `modified` | 원본 파일의 수정일 |
| `published` | 이 원본을 반영한 MkDocs 문서 경로 목록(**2단계에서 에이전트가 기록**, `handover/<건별-슬러그>/index.md`) |
| `needs_republish` | 원본이 바뀌거나 삭제되어 문서를 고쳐야 하면 `true`(**반영 후 에이전트가 `false`로 변경**) |

스크립트는 재실행해도 `published`와 `needs_republish`를 보존합니다. 에이전트가 고치는 필드는 이 두 개뿐입니다.

### 3.2 변환 결과 점검

`2. 변환 중간본/변환 보고서.md`를 읽고 다음을 사용자에게 보고합니다.

- 상태별 개수와 **조치가 필요한 파일**(실패, 미지원, 빈 결과) 목록과 조치 방법
- 사용자가 조치할 수 있는 항목(암호 해제, `.doc`→`.docx` 다시 저장, 압축 해제)이 있으면 조치 후 1단계를 다시 실행하도록 안내합니다. 이 항목 때문에 2단계를 멈추지는 않습니다.

## 4. 2단계: 인수자를 위한 건별 문서 작성과 MkDocs 등록

2단계의 목표는 **인수자가 인계자의 업무를 전반적인 흐름부터 쉽게 파악하게 하고, 그 문서가 인수자의 지식 기반으로 남아 이후 업무에 계속 쓰이게 하는 것**입니다. 판단이 갈릴 때는 가독성, 이해하기 쉬운 구성, 정돈된 서술을 무엇보다 우선합니다.

> **원본을 모두 옮기는 문서가 아닙니다.** 원본을 그대로 옮기는 전사도 아니고, 몇 줄로 줄여 버리는 요약도 아닙니다. 인수자가 업무를 수행하고 판단하는 데 필요한 **중요한 내용(4.3절의 기준표)은 빠짐없이 담고**, 그 밖의 세부는 문서에 싣지 않고 **출처로 찾아갈 수 있게** 합니다. 문서에 없는 세부를 나중에 질문받으면 6절에 따라 원본을 찾아 답합니다. 문서가 길어서 흐름이 보이지 않는 것은 내용이 부족한 것만큼 큰 문제입니다.

### 4.0 인수인계 건(Package) 식별 및 영문 슬러그 규칙

1. `1. RAW/` 바로 아래의 최상위 폴더가 개별 인수인계 건(패키지)의 단위입니다 (예: `1. RAW/업무인수인계_홍길동/`).
2. 폴더명과 자료의 내용에서 **기준 연도, 담당자명(인계자)**을 파악하여 영문 소문자·숫자·하이픈 조합의 고유 슬러그를 만듭니다.
    - 규칙: `YYYY-<person-name>` (예: `2024-hong-gildong`). 같은 해에 같은 인계자의 건이 둘 이상이면 `-<topic>`을 덧붙여 구별합니다.
3. **기준 연도 판별**:
    - 폴더명에 연도가 없거나 오타(예: `2004년 홍길동 인수인계 자료`와 같이 2024년이 잘못 적힌 경우)가 있을 때는, 원본 파일들의 작성일·수정일 및 문서 본문(예: 2023년 말 협의 결과, 2024년 사업 계획 등)을 대조하여 실제 기준 연도를 판별합니다.
    - 오타가 포함된 슬러그나 메뉴명을 쓰지 않고 올바른 실제 연도 슬러그(예: `2024-hong-gildong`)와 nav 한글 명칭(`2024년 홍길동`)을 부여합니다.
4. 한 건의 문서는 `mkdocs/docs/handover/<건별-슬러그>/` 폴더에 둡니다. 이 폴더의 **개요 문서(`index.md`)**와 **하위 문서(`<주제>.md`)**를 합쳐 이 스킬에서는 **건별 문서**라고 부릅니다. 나누는 기준은 4.4절에 있습니다.

### 4.1 내용 파악과 문서 구성 설계

1. 해당 건의 중간본을 **모두 읽습니다**(`converted`, `empty`, 텍스트를 확인할 수 있는 `unsupported`). 일부만 읽고 문서를 쓰기 시작하지 않습니다. 모두 읽어야 무엇이 중요한지 판단할 수 있습니다.
2. 내용을 원본 파일 단위가 아니라 **업무 단위**로 다시 묶습니다. 한 업무에 관한 설명이 인수인계서, 매뉴얼, 공문, 메신저 캡처에 흩어져 있으면 한 곳으로 모읍니다.
3. **전체 흐름을 먼저 정리합니다.** 업무 목록, 업무 사이의 관계(무엇이 무엇으로 이어지는지), 연간 흐름(언제 무엇을 하는지), 관계 기관과 역할을 먼저 정리해서 개요 문서의 앞부분을 설계합니다. 세부는 그다음에 정합니다. 이때 업무마다 다음 세 가지를 함께 가려 둡니다(정리 방법은 4.2.1절).
    - **반복 업무인지 일회성 업무인지**: 매년·분기·회차마다 돌아오는 업무와, 올해의 사업이나 사안처럼 한 번으로 끝나는 업무
    - **인계 시점에 어디까지 와 있는지**: 요약 표의 `기준 시점`을 기준으로 끝난 일, 진행 중인 일, 남은 일
    - **인수자의 몫이 무엇인지**: 여러 기관이 함께하는 절차에서 인수자(인계자의 자리)가 직접 하는 단계와, 다른 기관이 하고 인수자는 받거나 협조하는 단계
4. 업무마다 4.4절의 기준으로 **개요 문서 안에 둘지, 하위 문서로 나눌지**를 정합니다.
5. 문서 구성안(개요 문서의 장 제목, 하위 문서의 목록과 각 문서에 반영할 원본)을 사용자에게 제시하고, 답을 기다리지 않고 작성을 이어갑니다.

### 4.2 재구성 원칙 (가독성)

- **읽는 순서를 인수자의 관점으로 정합니다.** 전체 업무의 윤곽(무엇을, 언제, 누구와, 어떤 흐름으로)을 먼저 보여 주고, 업무별 핵심, 업무별 상세(하위 문서)의 순서로 내려갑니다. 원본 폴더의 순서나 파일명 순서를 따르지 않습니다.
- **결론과 할 일을 먼저 씁니다.** 각 절은 "이 업무가 무엇이고, 인수자가 언제 무엇을 해야 하는가"로 시작하고, 배경과 경위는 그 뒤에 둡니다. 질의와 회신, 협의 경위도 "무엇이 문제였고, 어떻게 결론이 났으며, 인수자가 할 일은 무엇인가"를 먼저 적고, 경위는 시간순 표로 정리합니다.
- **줄글을 구조화합니다.** 긴 문단은 표, 번호 절차, 다이어그램으로 바꾸고, 내용의 성격에 따라 아래 표현을 선택합니다.

| 내용의 성격 | 표현 |
| :--- | :--- |
| 업무 전체의 관계, 업무 사이의 연결 | Mermaid `flowchart` (개요 문서의 업무 지도) |
| 업무 목록, 담당·연락처, 계정·권한, 판본 비교, 주기별 일정 | 마크다운 표 |
| 업무 처리 순서, 결재·협의 흐름, 분기가 있는 절차 | Mermaid `flowchart` |
| 부서·시스템 사이에 주고받는 요청과 회신 | Mermaid `sequenceDiagram` |
| 문서나 건의 상태 변화(접수 → 검토 → 완료) | Mermaid `stateDiagram-v2` |
| 건수·예산·실적처럼 수치가 여러 개인 자료의 추이와 비교 | Vega-Lite 차트 (수치는 표로도 함께 제시) |
| 분기 없이 순서대로 실행하는 단계 | 번호 목록 |
| 놓치면 문제가 되는 기한, 주의 사항 | 알림 상자(`!!! warning`) |
| 실행할 SQL·스크립트, 문구 자체가 중요한 공문·지침 | 접이식 블록(`??? note "원문: 파일명"`). 블록 안의 내용은 4.3.1절에 따라 정리 |

- **다이어그램과 차트는 이해를 돕는 곳에 적극적으로 넣습니다.** 개요 문서에는 업무 전체의 흐름을 보여 주는 도표를 반드시 하나 이상 두고, 단계가 3개 이상이거나 분기·담당 전환이 있는 절차도 다이어그램으로 그립니다. 다만 표 한 개로 충분한 내용을 꾸미기 위해 넣지 않습니다. 작성 규칙과 미리 보기는 `mkdocs-writing-guide` 5.3·5.4절을 따릅니다.
- **반복된 내용은 한 번만 씁니다.** 같은 내용이 여러 판본(초안, 구버전, 최종안)이나 여러 파일에 있으면 최신 판본을 기준으로 한 번만 쓰고, 판본 사이에 달라진 점 가운데 업무에 영향이 있는 것만 표로 정리합니다. 같은 내용을 개요 문서와 하위 문서에 길게 되풀이하지 않습니다(개요 문서에는 핵심과 링크만 둡니다).
- **용어를 풀어 씁니다.** 원문에 설명 없이 쓰인 내부 용어와 약어는, 자료의 다른 부분에서 뜻을 확인할 수 있으면 처음 나오는 곳에 풀이를 덧붙입니다. 용어가 많으면 개요 문서에 `용어` 표를 둡니다. 확인할 수 없으면 `확인 필요`로 표시하고 질문지에 넣습니다.

### 4.2.1 연간 흐름과 업무 절차의 구성

인수자에게 가장 필요한 것은 "올해 무슨 일이 있었는가"보다 **"내년에도 같은 시기에 무엇을 해야 하는가"**와 **"지금 어디까지 와 있는가"**입니다. 인계 자료는 대개 한 해의 실적(공문, 회의자료)으로 이루어져 있으므로, 실적을 그대로 시간순으로 늘어놓지 않고 아래 기준으로 나누어 씁니다.

**연간 흐름은 두 표로 나눕니다.** 개요 문서의 `1. 업무 한눈에 보기`에 다음 두 표를 둡니다(골격은 `mkdocs-writing-guide` 4.2.1절). 반복 업무가 없는 건은 `올해 진행 현황`만 둡니다.

| 표 | 담는 내용 | 열 |
| :--- | :--- | :--- |
| `연간 반복 주기` | 매년 같은 시기에 돌아오는 일. 공문 번호나 특정 날짜를 빼고 월·분기 단위로 일반화합니다. | 시기, 업무, 할 일, 인수자 몫, 반복 근거 |
| `올해 진행 현황` | 기준 연도에 실제로 있었던 일과 남은 일. 실제 날짜와 근거 문서를 적습니다. | 시기, 업무, 실제 일정, 상태 |

- **반복이 확인된 근거**: 다음 가운데 하나가 있으면 반복이 확인된 것으로 보고, 그 근거를 `반복 근거` 칸에 적습니다. ① 적용 기간을 한정하지 않은 규정·지침에 주기가 정해져 있음(예: 훈령의 "매년 3월까지 제출") ② 두 해 이상의 자료에서 같은 시기에 같은 일이 나옴 ③ 인수인계서나 질문지 답변에서 인계자가 매년 하는 일이라고 적음.
- **기준 연도의 근거만 있는 경우**: `2026년 운영 계획`처럼 그해에만 적용되는 계획서의 일정이나, 기준 연도의 실적만 있는 일은 반복이 확인된 것이 아닙니다. 이런 일도 반복 주기 표에 넣되, `반복 근거` 칸에 실제 근거와 함께 `반복 여부 확인 필요`라고 적고(예: `2026년 운영 계획의 분기별 일정 · 반복 여부 확인 필요`) 질문지에 넣습니다(`handover-questionnaire` 2.2절의 `주기·준비 기간` 유형). 매년 반복될 것이라고 추측해서 단정하지 않습니다.
- **계획과 실적이 다른 경우**: 계획서의 시기와 실제 일정이 다르면(예: 계획은 2&#47;4분기, 실제 개최는 7월) 반복 주기 표의 `시기`에 두 값을 함께 적습니다.
- **상태 값**: `올해 진행 현황`의 `상태`는 `완료`, `진행 중`, `예정`, `확인 필요` 가운데 하나입니다. 일정이 기준 시점보다 앞서고 결과 자료(결과 안내 공문, 회의록, 보고서)가 있으면 `완료`, 기준 시점에 걸쳐 있으면 `진행 중`, 기준 시점보다 뒤이면 `예정`, 일정이 지났는데 결과 자료가 없으면 `확인 필요`입니다. 표의 제목이나 바로 아래에 기준 시점을 적습니다.
- 연간 흐름은 Mermaid `gantt`가 아니라 표로 씁니다. 사이트의 Mermaid 렌더러가 `gantt`를 지원하지 않고(`mkdocs-writing-guide` 5.3절), 표가 날짜와 상태를 함께 보여 주기에 알맞습니다.

**반복 업무의 절차는 다음 회차에 그대로 따라 할 수 있게 씁니다.** 단계가 셋 이상인 반복 업무(협의회 개최, 연례 조사, 연말 정산 등)는 흐름도 아래에 단계별 표를 두고, 다음 항목을 담습니다.

| 항목 | 내용 | 자료에 없을 때 |
| :--- | :--- | :--- |
| 시작 신호 | 그 업무가 무엇으로 시작되는지(상급 기관 공문 접수, 정해진 월, 요청 접수) | `확인 필요` |
| 단계와 하는 일 | 단계마다 하는 일 | (자료에 있는 단계만 적음) |
| 담당 | 단계마다 하는 기관·역할. 인수자가 직접 하는 단계는 `**인수자**`로 시작해 구별하고, 다른 기관이 하는 단계에는 인수자가 받는지, 협조하는지를 적습니다. | `확인 필요` |
| 산출물·전례 자료 | 그 단계에서 만들거나 받는 문서와, 다음 회차에 고쳐 쓸 직전 회차의 자료(공문, 계획, 서식)의 원본 경로 | 산출물을 받지 못했으면 `자료 누락` |
| 회차별 실제 날짜 | 자료에 있는 회차마다 그 단계의 실제 날짜 | 빈칸 |

- **준비 기간(리드타임)은 계산하지 않습니다.** "개최 4주 전까지"처럼 원문에 준비 기간이 적혀 있으면 그대로 옮깁니다. 적혀 있지 않으면 회차별 실제 날짜만 나란히 적고, 날짜 사이의 간격을 계산해서 "약 5주 전"처럼 쓰지 않습니다. 준비 기간은 `확인 필요`로 두고 질문지에 넣습니다. 계산한 값은 원문에 없는 수치이고, 회차마다 사정이 달라 기준으로 삼기 어렵기 때문입니다.
- 일회성 사업(올해의 시범 사업, 특정 사안)은 회차별 표 대신 경위를 시간순 표로 정리하고, 인계 시점의 상태와 남은 일을 먼저 씁니다(4.2절의 "결론과 할 일을 먼저 씁니다").
- 반복 업무의 하위 문서에는 다음 회차를 준비할 때 볼 `전례 자료` 목록(직전 회차의 공문·계획·서식·결과의 원본 경로)을 한 곳에 모아 둡니다. 출처가 "이 내용의 근거"라면, 전례 자료는 "다음에 고쳐 쓸 문서"입니다.

### 4.3 내용 선별과 보존 원칙

무엇을 문서에 담을지는 아래 기준표로 판단합니다. **기준표에 해당하는 내용은 빠짐없이 담고, 사실은 바꾸지 않습니다.** 기준표에 해당하지 않는 세부는 문서에 싣지 않아도 되지만, 출처를 통해 원본에서 찾을 수 있어야 합니다.

| 반드시 담는 내용 (중요 내용) | 출처로 연결하고 문서에 싣지 않아도 되는 내용 |
| :--- | :--- |
| 업무의 목적, 범위, 인수자가 맡는 역할 | 회의의 발언 순서별 기록, 토의 내용 전체(결정 사항과 후속 조치는 담음) |
| 수행 절차와 방법(메뉴 경로, 입력값, 실행할 쿼리) | 공문·계획서·보고서의 전문(결정 내용과 인수자에게 미치는 영향은 담음) |
| 일정, 기한, 주기, 반복 여부와 그 근거, 업무의 시작 신호 | 이미 끝난 일의 세부 경위(결과와 지금도 유효한 결정은 담음) |
| 절차의 단계마다 인수자가 직접 하는 일과 다른 기관의 몫, 다음 회차에 고쳐 쓸 전례 자료의 위치 | |
| 담당 부서·역할, 연락할 상대의 연락처, 협조 관계 | 참석자 명부, 서명부, 배부 목록 같은 행정 세부 |
| 시스템, 접속 주소, 계정, 권한 신청 방법 | 같은 서식의 반복, 빈 양식의 칸 구성 |
| 진행 중인 사안의 현재 상태와 다음 조치 | 수백 행의 원자료 표(집계와 업무에 쓰는 행은 담음) |
| 결정·합의 사항, 판단 기준, 예외, 주의 사항 | 인사말, 추진 배경의 일반론처럼 업무 수행과 관계없는 서술 |
| 업무 판단에 쓰이는 수치(예산, 실적, 건수, 목표) | |
| 자료 사이의 불일치, 자료에 없어 확인이 필요한 부분 | |

- **애매하면 담는 쪽을 택하되, 위치를 낮춥니다.** 중요한지 판단하기 어려운 내용은 개요 문서가 아니라 하위 문서에, 본문이 아니라 표나 접이식 블록에 둡니다. 개요 문서의 흐름을 해치면서까지 세부를 넣지 않습니다.
- **표현 방식을 바꿀 때 중요 내용을 잃지 않습니다.** 문단을 표나 다이어그램으로 바꿀 때 중요 내용은 표의 칸, 노드와 연결선, 도표 아래의 설명 가운데 어딘가에 남아 있어야 합니다. 다이어그램에 담지 못한 조건이나 단서는 도표 바로 아래에 불릿으로 적습니다.
- **사실은 바꾸지 않습니다.** 수치, 날짜, 금액, 기관·부서·사람 이름, 연락처, 계정, 접속 주소, 메뉴 경로, 문서 번호는 원문의 값 그대로 옮깁니다. 줄여 쓰더라도 값을 반올림하거나 바꾸지 않습니다. 사이트는 사용자 본인만 보므로 개인정보를 가리지 않습니다.
- **추측으로 채우지 않습니다.** 자료에 없는 단계, 담당, 일정을 그럴듯하게 만들어 넣지 않습니다. 비어 있는 부분은 `확인 필요`라고 적고 개요 문서의 `## 인수인계 확인 사항`에 있는 `미결 사항`에 모읍니다.
- **다이어그램과 차트에는 원문에 근거가 있는 단계와 수치만 넣습니다.** 흐름을 매끄럽게 보이게 하려고 원문에 없는 노드나 값을 추가하지 않습니다.
- **출처를 적습니다.** `###` 단위의 절 끝에 `출처: \`별첨자료/파일명.hwp\``와 같이 근거가 된 원본의 경로를 적어서, 인수자와 에이전트가 문서에 싣지 않은 세부를 원본에서 찾아볼 수 있게 합니다. 세부를 덜어 낸 절일수록 출처를 정확하게 적습니다(필요하면 `회의록 4쪽`, `시트 '집계'`처럼 위치까지 적습니다). 원본 경로는 모두 **건 폴더 기준 상대 경로**이며, 건 폴더의 이름은 개요 문서의 `## 요약` 표에 있는 `**원본 자료**` 행에 적습니다.
- **전문은 꼭 필요할 때만 접이식 블록에 둡니다.** 그대로 실행해야 하는 SQL·스크립트, 문구 자체가 업무 기준이 되는 공문·지침, 값을 그대로 써야 하는 표만 `??? note` 블록에 전문을 넣습니다. 블록 위에는 그 자료가 무엇을 하는지(무엇을 하는 쿼리인지, 공문이 무엇을 정하는지) 설명을 둡니다. 읽어 볼 필요가 있을 뿐인 자료는 전문을 싣지 않고 출처로 연결합니다.
    - 공공기관 및 Windows 환경에서 작성된 스크립트·SQL 파일은 종종 **`UTF-16LE`(BOM 포함) 또는 `CP949`**로 인코딩되어 일반 텍스트 읽기에서 실패하거나 바이너리로 취급될 수 있습니다. Python(`open(..., encoding='utf-16le', errors='replace')`) 등으로 내용을 정확히 확인한 뒤 코드 블록(` ```sql `, ` ```bash `)으로 전문을 수록합니다.
- **모든 원본을 추적합니다.** 내용이 거의 없는 파일(빈 양식, 메모)을 포함하여 해당 건의 모든 원본이 개요 문서의 `원본 파일 대응표`에 들어 있어야 합니다. 반영한 원본(`converted`·`empty`, 그리고 `.sql`처럼 에이전트가 텍스트로 직접 읽어 반영한 `unsupported`)에는 반영한 문서와 절을, 내용을 읽었지만 중요 내용이 없어 반영하지 않은 원본에는 `참고용(문서에 싣지 않음)`과 한 줄 설명을, 반영하지 못한 원본(`failed`와 나머지 `unsupported`)에는 상태와 조치 방법을 적습니다. 이 대응표는 나중에 질문을 받았을 때 원본을 찾아가는 색인이 됩니다.
- **작성을 마친 뒤 점검합니다.** 중간본을 파일별로 다시 훑으면서 기준표의 항목(절차, 일정, 담당·연락처, 계정, 진행 중 사안, 결정 사항, 수치)이 문서에 모두 들어갔는지 확인합니다. 그다음 개요 문서만 처음부터 끝까지 읽어 보고, 업무의 전체 흐름과 인수자가 먼저 할 일이 보이는지, 세부에 가려 흐름이 끊기는 곳이 없는지 확인합니다.
- **인수자의 입장에서 따라 해 봅니다.** 마지막으로, `연간 반복 주기`에서 기준 시점 이후 처음 돌아오는 반복 업무를 하나 고르고, 문서만 읽고 다음 네 가지를 찾을 수 있는지 확인합니다. ① 언제, 무엇을 계기로 시작하는가 ② 인수자가 처음 할 일은 무엇인가 ③ 누구에게 연락하는가 ④ 고쳐 쓸 전례 자료는 어디에 있는가. 찾을 수 없는 항목이 자료에도 없으면 `확인 필요`로 표시하고 질문지에 넣습니다. 반복 업무가 없는 건은 `진행 중인 사안`의 첫 사안으로 같은 확인을 합니다.

### 4.3.1 원문 블록 정리 규칙 (중간본을 그대로 붙이지 않는다)

접이식 블록에 넣는 "원문"도 화면에서 읽는 글입니다. 중간본은 변환 도구가 원본의 겉모양을 기계적으로 옮긴 결과여서, 그대로 붙이면 표와 서식이 깨져 보입니다. 원문 블록은 **문구는 그대로 두고 마크업만 고쳐서** 넣으며, 스크립트로 여러 블록을 한꺼번에 옮길 때도 아래 규칙을 스크립트에 반영합니다.

| 중간본에 나타나는 모양 | 원인 | 옮기는 방법 |
| :--- | :--- | :--- |
| `\| Ⅰ \|  \| 목 적 \|`처럼 제목 줄만 있는 표 | 한글 문서의 장·절 제목 상자 | 굵은 제목(`**Ⅰ. 목 적**`)으로 바꿉니다. 블록 안에서는 `#` 제목을 쓰지 않습니다. |
| 빈 칸만 있는 행·열이 섞인 표, 칸의 대부분이 빈 표 | 조직도·절차도 같은 도식을 표로 그린 것 | 빈 행·열을 없애고 병합 값(`rowspan`·`colspan`)을 맞춥니다. 도식이면 상자의 배치나 단계를 읽을 수 있는 표로 다시 짜고, 선·화살표가 변환되지 않았다는 사실을 한 줄로 적습니다. |
| 문단마다 뒤따르는 2KB 미만의 같은 그림 | 그림으로 넣은 글머리표 | 그림을 지우기 전에 앞 문단을 목록 항목으로 바꿉니다. 작은 그림을 일괄 제거하기 전에 **그 그림이 무엇인지 한 장은 열어 봅니다.** |
| `□`, `❍`, `-`, `※`로 시작하는 문단이 모두 같은 수준으로 나열됨 | 글머리표의 들여쓰기 수준이 변환되지 않음 | `□`는 굵은 소제목, `❍`·`○`는 1수준 목록, `-`·`·`는 2수준 목록, `※`는 바로 앞 항목의 하위 항목으로 옮깁니다(4칸 들여쓰기). 문서마다 기호의 위계가 다르므로 옮기기 전에 원본의 위계를 확인합니다. |
| 글머리표 없이 이어지는 짧은 줄, 낱말 중간에서 끊긴 줄 | 원본의 줄바꿈이 문단으로 변환됨 | 앞 항목에 이어 붙입니다. 낱말이 끊긴 경우에만 붙여 쓰고, 그 사실을 블록 첫 줄에 적습니다. |
| 표의 한 칸에 `<br>`로 이어진 긴 본문(회의록의 "주요 회의내용" 칸 등), 표 안의 표 | 본문 전체를 표의 한 칸에 넣은 서식 | 그 행을 표 밖으로 꺼내어 목록과 표로 풉니다. 중첩된 표는 `<table>`의 깊이를 세어 통째로 다룹니다. |
| 공문 PDF에서 수신자·결재·시행 정보가 흩어지고 순서가 섞임 | PDF의 글자 배치 순서대로 추출됨 | 공문의 항목(발신 기관, 수신, 제목, 본문, 붙임, 발신 명의, 수신자, 결재, 시행·접수, 주소·연락처)별 표로 다시 묶습니다. 추출이 의심스러운 글자는 고치지 않고 `원본 PDF로 확인 필요`라고 적습니다. |
| 엑셀 표의 오른쪽 끝에 붙은 제목 없는 열, 값 몇 개만 있는 시트 | 선택 목록(드롭다운)용 값, 보조 열 | 표에서 빼고, 어떤 값이 있었는지를 블록 첫 줄에 적습니다. 말없이 지우지 않습니다. |
| `1.`, `2.`로 시작하는 문단 | 마크다운이 순서 목록으로 해석하여 번호를 1부터 다시 매김 | `1\.`처럼 점을 이스케이프하여 원본의 번호가 그대로 보이게 합니다. |
| 표지·간지에서 두 번씩 반복된 글자, 문서 머리의 조각 글자 | 겹쳐 놓은 글상자, 숨은 글자 | 반복은 한 번만 남기고, 뺀 것이 있으면 완료 보고에 적습니다. |
| 작성용 빈 서식(빈 글머리표, 빈 칸) | 내용을 채우도록 만든 양식 | 빈 자리를 `(작성 칸)`·`(빈칸)`으로 표시하여 서식의 모양이 보이게 합니다. |

- **블록 첫 줄에 옮긴 방식을 적습니다.** 표로 다시 짰거나, 끊긴 낱말을 이어 붙였거나, 보조 열을 뺀 블록에는 `옮긴 방식:`으로 시작하는 한 줄을 둡니다.
- **병합 칸이 있는 표는 HTML 표를 유지합니다.** 이때 `??? note` 대신 `<details class="note" markdown="1">`을 쓰고, 표를 `<div class="md-typeset__scrollwrap"><div class="md-typeset__table">`로 감쌉니다. 블록 안의 목록은 들여쓰기 0칸에서 시작합니다(첫 항목을 4칸 들여 쓰면 코드 블록으로 표시됩니다).
- **기계적으로 옮긴 블록은 화면으로 검수합니다.** 스크립트로 옮겼다면, 빌드한 HTML에서 블록마다 다음을 자동으로 세어 0건인지 확인합니다: 글자로 드러난 표 기호(`|---|`)와 태그(`&lt;table`), 빈 행, 칸이 하나뿐인 표, 기호만 있는 문단, 코드 블록으로 바뀐 목록(`<pre>`). 그 뒤에 **원본의 종류(공문, 계획 문서, 회의록, 회의자료 안건, 엑셀 서식, 발표 자료)마다 최소 한 블록을 브라우저에서 펼쳐** 눈으로 확인합니다. 자동 점검은 "위계가 사라진 문단"을 잡지 못하므로 눈으로 보는 확인을 생략하지 않습니다.
- **고치기 전과 후의 낱말을 비교합니다.** 마크업을 정리한 뒤에는 정리 전 문서와 낱말 단위로 비교하여, 사라진 낱말이 의도한 것(반복된 간지 글자, 이어 붙인 낱말 조각)뿐인지 확인합니다.

### 4.4 개요 문서와 하위 문서의 구성

건별 문서는 **개요 문서 하나와, 깊이 들어가야 하는 업무만 따로 떼어 낸 하위 문서**로 구성합니다. 원본 파일별로 문서를 나누지 않고, 업무(주제) 단위로 나눕니다.

| 문서 | 역할 | 들어가는 내용 |
| :--- | :--- | :--- |
| 개요 문서 `<건별-슬러그>/index.md` | 인수자가 가장 먼저, 처음부터 끝까지 읽는 문서. 업무의 전체 흐름을 파악하게 하고 하위 문서로 안내합니다. | 요약, 업무 지도, 연간 반복 주기와 올해 진행 현황(4.2.1절), 업무별 핵심(하는 일, 시기, 상대, 주의 사항)과 하위 문서 링크, 시스템·연락처 요약, 진행 중인 사안, 원본 파일 대응표, 질문지 관련 섹션, 인수인계 확인 사항 |
| 하위 문서 `<건별-슬러그>/<주제>.md` | 특정 업무를 실제로 수행하거나 자세히 찾아볼 때 읽는 문서 | 그 업무의 상세 절차(4.2.1절의 단계별 표), 회차·연도별 이력, 판단 기준과 예외, 다음 회차의 전례 자료, 참고 자료(명단, 계정 목록), 필요한 원문 블록 |

**하위 문서로 나누는 기준**: 아래 가운데 하나에 해당하면 그 업무를 하위 문서로 떼어 내고, 개요 문서에는 그 업무의 핵심 요약(5~15줄 정도)과 링크만 남깁니다.

- 그 업무의 상세를 개요 문서에 쓰면 **약 100줄을 넘는** 경우
- 단계가 많은 절차, 회차별 기록(예: 1차·2차 협의회), 사업의 연도별 경위처럼 **따로 찾아볼 상세**가 있는 경우
- 명단, 계정 목록, 코드표처럼 **찾아보는 용도의 참고 자료**가 긴 경우(예: `contacts.md`)

**분량의 목표와 구성 규칙**:

- 개요 문서는 표와 도표를 포함해 **약 300~500줄**을 목표로 합니다. 이보다 길어지면 하위 문서로 옮길 절이 없는지 먼저 검토합니다.
- 하위 문서 하나가 **약 600줄**을 넘으면 업무 단위로 다시 나눌 수 있는지 검토합니다.
- 업무가 적고 자료가 짧은 건은 하위 문서 없이 개요 문서 하나로 끝내도 됩니다. 나누는 것 자체가 목적이 아닙니다.
- 하위 문서는 건 폴더 바로 아래에 평탄하게 두고, 폴더를 더 만들지 않습니다(`handover/<건별-슬러그>/council.md`). 파일명은 업무를 나타내는 영문 소문자·숫자·하이픈 조합입니다.
- 하위 문서는 개요 문서만 읽고 들어온 독자도, 검색으로 바로 들어온 독자도 이해할 수 있게 씁니다. 첫머리에 이 문서가 다루는 업무를 한 문장으로 설명하고 개요 문서로 돌아가는 링크를 둡니다.
- 미결 사항, 질문지 현황, 인계자 보충 답변, 원본 파일 대응표는 **개요 문서에만** 둡니다. 하위 문서의 `확인 필요`도 개요 문서의 `미결 사항`에 모으고, 해당 하위 문서의 절로 링크합니다.

각 문서의 골격과 서식은 `mkdocs-writing-guide` 4.2절을 따릅니다.

### 4.5 경로, 이미지, 네비게이션

- **문서 파일 경로**: 개요 문서는 `mkdocs/docs/handover/<건별-슬러그>/index.md`, 하위 문서는 `mkdocs/docs/handover/<건별-슬러그>/<주제>.md`
- **이미지 경로 및 포맷 변환 (필수)**:
    - 경로: `mkdocs/docs/handover/<건별-슬러그>/images/` (파일명은 영문 소문자·숫자·하이픈). 한 건의 개요 문서와 하위 문서가 이 폴더를 함께 씁니다. 이미지가 많으면 파일명 앞에 하위 문서 이름을 붙여(`council-screen-01.png`) 구별합니다.
    - **BMP 포맷의 PNG 변환**: HWP/HWPX 문서에서 추출된 이미지가 `.bmp` 포맷인 경우, 웹 브라우저(Chrome, Safari 등)에서 정상 렌더링되지 않거나 용량(장당 수 MB)으로 인해 로딩이 지연됩니다. 전용 폴더로 이전할 때 반드시 **Pillow(PIL) 라이브러리를 사용하여 `.png`로 변환**하여 저장하고 마크다운 본문에도 `.png` 확장자로 링크합니다.
    - **불필요한 공문 직인/로고 제외**: 공문서 하단에 관행적으로 반복 첨부되는 기관 직인/도장/로고(예: KERIS 직인 `image_001.png` 등 22KB 내외 동일 이미지)는 이전 대상에서 제외하고, 본문 이해에 필수적인 **시스템 UI 캡처 화면만 선별 이전**합니다. 이미지에는 무엇을 보여 주는 화면인지 설명을 함께 적습니다.
    - **이미지와 설명 텍스트 간 개행(빈 줄) 유지 (필수)**: 마크다운 본문에 이미지를 삽입할 때는 `![이미지](...)` 태그 위아래에 반드시 1줄 이상의 빈 줄(Blank line)을 삽입합니다. 빈 줄이 없으면 동일한 단락(`<p>`) 내 인라인으로 처리되어 브라우저에서 이미지 바로 우측에 설명 텍스트가 한 줄로 나란히 이어 붙는 심각한 레이아웃 왜곡이 발생합니다(`mkdocs-writing-guide` 2.9절). 여러 이미지를 연속 배치할 때도 각 이미지와 하단 설명 리스트 사이에 빈 줄을 둡니다.
- **네비게이션(`nav`) 등록**:
    - `인수인계` 탭의 첫 항목은 항상 마스터 허브인 `handover/index.md`입니다.
    - 그 아래에 인수인계 건마다 **섹션 하나**를 두고, 섹션의 첫 항목에 개요 문서(`index.md`)를 제목 없이 적은 뒤 하위 문서를 읽는 순서대로 적습니다. `navigation.indexes`가 켜져 있으므로 섹션 이름을 누르면 개요 문서가 열립니다. 하위 문서가 없는 건은 기존처럼 한 항목으로 등록합니다.
    - **좌측 메뉴 폭 제한 및 한 줄 표시 규칙 (필수)**: 좌측 사이드바 메뉴는 폭이 제한되어 있어 글자 수가 길어지면 두 줄로 줄바꿈됩니다. 따라서 건의 섹션 이름에 부서나 업무명(예: `(K-에듀파인 업무관리)`)을 덧붙이지 않고, 반드시 **`YYYY년 <담당자명>`** (예: `2024년 홍길동`) 형태로 지정합니다. 하위 문서의 메뉴명도 12자 안팎의 업무 이름으로 짧게 짓습니다(예: `업무협의체 운영`). 소관 업무 및 부서 등의 상세 정보는 개요 문서의 `## 요약`과 마스터 허브 표에 적습니다.

```yaml
nav:
  - 홈: index.md
  - 인수인계:
      - handover/index.md # 마스터 허브 (전체 인수인계 목록)
      - 2024년 홍길동: # 건별 섹션 (섹션 이름을 누르면 개요 문서가 열림)
          - handover/2024-hong-gildong/index.md # 개요 문서
          - 업무협의체 운영: handover/2024-hong-gildong/council.md # 하위 문서
          - 관계자 명단: handover/2024-hong-gildong/contacts.md
      - 2025년 홍길동: handover/2025-hong-gildong/index.md # 하위 문서가 없는 건
```

### 4.6 마스터 허브와 홈

1. **마스터 허브 페이지 (`mkdocs/docs/handover/index.md`)**:
    - 사이트의 모든 인수인계 건을 총괄 안내하는 포털 페이지입니다.
    - `## 요약`: 전체 인수인계 건 목록 표 (인수인계 건명, 담당자/부서, 소관 업무/시스템, 기준 연월, 원본 수, 상태, 개요 문서 바로가기 링크).
    - `상태`에는 진행 단계를 적습니다: `1차 등록`(2단계 완료) → `질문지 회신 대기`(3단계 완료) → `일부 미회신` 또는 `보강 완료`(4단계 완료).
    - `## 1. 등록된 인수인계 건별 안내`: 각 건의 소관 업무, 주요 내용, 개요 문서와 주요 하위 문서의 바로가기 링크.
    - `## 2. 인수인계 자료 탐색 및 신규 등록 가이드`: 사이드바 탐색 및 추가 절차 안내.
2. **홈(`mkdocs/docs/index.md`)**: 요약 표의 `인수인계 자료` 행과 최근 업데이트 표의 건별 행을 `mkdocs-writing-guide` 3.4절에 따라 갱신합니다.

### 4.7 manifest 일괄 갱신 가이드

- 원본 항목의 `published`에는 그 원본의 내용을 반영한 **문서의 경로를 모두** 배열로 기록하고(`handover/<건별-슬러그>/index.md`, `handover/<건별-슬러그>/council.md` 등), `needs_republish`를 `false`로 설정합니다. 하위 문서에만 반영한 원본도, 원본 파일 대응표가 개요 문서에 있으므로 개요 문서의 경로를 함께 넣습니다.
- 내용을 읽었지만 중요 내용이 없어 `참고용(문서에 싣지 않음)`으로 대응표에 적은 원본도, 대응표에 반영되었으므로 개요 문서의 경로를 기록합니다.
- 반영하지 못한 원본(`failed`, 내용을 확인하지 못한 `unsupported`)은 `published`에 넣지 않습니다.
- 원본이 많으면 누락이 생기기 쉬우므로 Python 스크립트로 일괄 갱신합니다:
    ```python
    import json
    with open('2. 변환 중간본/manifest.json', 'r', encoding='utf-8') as f:
        data = json.load(f)
    prefix = '업무인수인계_홍길동/'
    base = 'handover/2024-hong-gildong/'
    # 원본 상대 경로(prefix 제외) → 반영한 하위 문서. 여기에 없으면 개요 문서에만 반영한 원본입니다.
    sub_docs = {'회의자료/1차 협의회 결과.hwp': ['council.md']}
    read_directly = {'<file-id>'}  # 텍스트로 직접 읽어 반영한 unsupported 원본의 ID
    for fid, entry in data['files'].items():
        if not entry['source'].startswith(prefix):
            continue
        if entry['status'] in ('converted', 'empty') or fid in read_directly:
            rel = entry['source'][len(prefix):]
            entry['published'] = [base + 'index.md'] + [base + d for d in sub_docs.get(rel, [])]
            entry['needs_republish'] = False
    with open('2. 변환 중간본/manifest.json', 'w', encoding='utf-8') as f:
        json.dump(data, f, ensure_ascii=False, indent=2)
    ```

### 4.8 등록 후 이어지는 단계 (질문지 작성)

2단계가 끝나면 사용자에게 묻지 않고 `.agents/skills/handover-questionnaire/SKILL.md`를 읽어 3단계(질문지 작성)를 이어서 수행합니다.

- 문서를 쓰는 동안 `확인 필요`로 표시한 부분과 개요 문서의 `## 인수인계 확인 사항`에 있는 `미결 사항`(절차·담당·일정이 빠진 부분, 본문에서 언급되지만 받지 못한 파일, 자료 간 불일치)이 3단계에서 질문을 뽑는 출발점이 됩니다.
- 변환하지 못한 원본(`failed`, `unsupported`) 가운데 사용자가 조치할 수 없는 것(인계자만 가진 암호, 인계자 PC에만 있는 파일)은 질문지에 `자료 누락` 유형으로 넣습니다.

## 5. 원본이 바뀌었을 때 (증분 갱신)

1. `convert.py`를 다시 실행합니다. 새 파일만 변환되고, 바뀐 파일은 재변환되며, 삭제된 파일은 `removed`로 표시됩니다.
2. 기존 인수인계 건에 파일이 추가·변경된 경우에는 그 내용이 속한 업무의 문서(개요 문서나 하위 문서)를 고쳐 씁니다. 이때도 4.3절의 기준표로 담을 내용을 고르며, 고친 결과 문서가 4.4절의 분량을 넘으면 하위 문서로 나눕니다. 개요 문서의 원본 파일 대응표와, 고친 문서의 최종 수정일을 갱신합니다.
3. 완전히 새로운 인수인계 건(새 상위 폴더)이 들어온 경우:
    - 새 건별 슬러그 디렉터리에 개요 문서(`index.md`)와 필요한 하위 문서 작성
    - `mkdocs.yml`의 `nav`에 새 인수인계 건의 섹션(또는 항목) 추가
    - 마스터 허브(`handover/index.md`) 표에 새 건 행 추가
    - 홈(`index.md`) 최근 업데이트 표 갱신
4. `manifest.json`을 갱신하고 빌드 검증을 수행합니다.
5. 완전히 새로운 인수인계 건이면 4.8절에 따라 3단계(질문지 작성)까지 수행합니다. 기존 건에 자료가 추가된 경우에는 새 자료에서 생긴 의문점을 사용자에게 보고하고, 사용자가 요청하면 새 작성일로 질문지를 하나 더 만듭니다.
6. 건별 문서가 4단계에서 이미 보강되어 있다면, 원본 변경을 반영할 때 질문지 답변으로 채운 내용(`질문지 YYMMDD · Q-NNN` 표기가 붙은 부분)과 `## 인계자 보충 답변` 섹션을 지우지 않고 보존합니다. 문서를 나누거나 합칠 때도 이 표기를 내용과 함께 옮깁니다.
7. 사용자가 이미 등록된 건을 이 스킬의 현재 기준(개요 문서와 하위 문서)으로 다시 구성해 달라고 요청하면, 기존 문서를 지우고 새로 쓰지 않고 기존 문서의 내용(특히 질문지 답변과 `확인 필요` 표시, 출처)을 4.3·4.4절에 따라 옮겨 나눕니다. 덜어 낸 세부가 원본에서 찾을 수 있는 것인지 출처로 확인하고, `nav`와 `published`의 경로를 함께 고칩니다.

## 6. 문서에 없는 내용을 질문받았을 때

건별 문서는 중요한 내용만 담으므로, 인수자가 문서에 없는 세부(회의에서 누가 무엇을 말했는지, 공문의 정확한 문구, 원자료 표의 특정 값)를 물어볼 수 있습니다. 이때는 원본을 찾아 답합니다.

1. **문서에서 먼저 찾습니다.** 해당 건의 개요 문서와 하위 문서를 검색합니다. 답이 있으면 문서의 위치(문서와 절)와 함께 답합니다.
2. **문서에 없으면 원본을 찾습니다.** 개요 문서의 `원본 파일 대응표`와 절마다 적힌 `출처`로 관련 원본을 고르고, `2. 변환 중간본/`의 해당 중간본을 읽습니다. 어느 원본인지 알 수 없으면 중간본 전체에서 관련 낱말을 검색합니다(`grep -rn "낱말" "2. 변환 중간본/"`). 중간본으로 확인하기 어려운 내용(그림 속 글자, 깨진 표)은 `1. RAW/`의 원본을 직접 열어 확인합니다.
3. **출처와 함께 답합니다.** 답에는 근거가 된 원본의 경로(건 폴더 기준 상대 경로)와 위치(쪽, 시트, 슬라이드)를 적습니다. 원본에도 없으면 없다고 답하고, 인계자에게 물어볼 사항이면 질문지에 넣을 수 있다고 안내합니다. 추측으로 답하지 않습니다.
4. **지식 기반을 키웁니다.** 찾은 내용이 4.3절 기준표의 중요 내용인데 문서에 빠져 있었다면, 해당 절에 보충하고 출처를 붙인 뒤 그 사실을 답변에 알립니다(실질적인 변경이므로 최종 수정일과 홈을 갱신하고 빌드 검증을 합니다). 중요 내용은 아니지만 업무를 하면서 다시 찾을 만한 내용이면, 문서에 보충할지 한 줄로 제안합니다.
